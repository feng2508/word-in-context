# Repository Guidelines

## Project Structure & Module Organization

This is a WXT browser extension written in TypeScript and React. Source code is in `src/`:

- `src/entrypoints/` contains extension entry points: the background worker, content script, popup, and side panel.
- `src/components/` contains reusable React UI, such as `ExplainButton.tsx` and `ExplainSelection.tsx`.
- `src/hooks/` contains browser-page behavior and shared UI state; `useSelectionData.ts` owns selected text, its sentence, and button coordinates.
- `public/` holds extension icons and static assets. Build output is generated by WXT and must not be committed.

Keep browser-specific message handling in entry points. Pass typed data between UI components rather than reading browser APIs throughout the component tree.

## Build, Test, and Development Commands

Use Bun, as indicated by `bun.lock`:

```zsh
bun install          # install dependencies and run WXT preparation
bun run dev          # start Chrome development mode
bun run dev:firefox  # start Firefox development mode
bun run compile      # run TypeScript checks without emitting files
bun run build        # create a production Chrome build
bun run zip          # package the Chrome extension
```

Run `bun run compile` before committing. Run `bun run build` when changing WXT configuration, permissions, or extension entry points.

## Coding Style & Naming Conventions

Use TypeScript, React function components, and two-space indentation. Name components and types in PascalCase (`ExplainSelection`, `SelectionData`); name hooks with the `use` prefix; use camelCase for functions, variables, and browser message fields. Keep files focused and colocate types with their owning hook or component when they are not reused elsewhere.

Model optional UI state explicitly, for example `SelectionData | null`, and check it before rendering or sending messages. Preserve the current asynchronous `browser.runtime` and `browser.storage` patterns.

## Testing Guidelines

No automated test framework is configured yet. At minimum, run `bun run compile` and manually verify selection, Explain-button placement, side-panel opening, and selection persistence in a browser. Add tests alongside new complex parsing or data-transformation logic, using descriptive names such as `useSelectionData.test.ts`.

## Commit & Pull Request Guidelines

Follow the established Conventional Commit style: `feat(sidepanel): display selected word and sentence`, `fix: hide explain button after click`, or `refactor: separate selection UI components`. Keep each commit scoped to one change.

Pull requests should describe the user-visible behavior, list verification commands, link related issues when applicable, and include screenshots or a short recording for popup, content-script, or side-panel UI changes. Never commit API keys; add any new extension permissions deliberately in `wxt.config.ts`.
